## Problem

`omarchy version` takes about **45 ms**. It answers from two `pacman -Q`
calls. The other 44 ms is the dispatcher re-deriving a routing table it could
have derived once.

`/usr/bin/omarchy` is a **1,091-line** bash script. On every invocation it:

- globs every `omarchy-*` (445 of them),
- reads up to `METADATA_SCAN_LIMIT=80` lines of each header,
- parses `omarchy:summary`, `omarchy:group`, `omarchy:args`, `omarchy:alias`,
  `omarchy:hidden`, `omarchy:requires-sudo`,
- builds ~15 associative arrays and a collision-checked route table,
- then resolves the route and `exec`s the real binary.

Measured: `omarchy version` ≈ 45 ms, `omarchy theme list` ≈ 11 ms.

The command metadata is already **declarative** — it is comments in a header
block, and 443 of 445 commands carry it. The system is re-parsing its own
declaration on every run.

Worth stating plainly: this has already been optimized once. `METADATA_SCAN_LIMIT`
exists, and the route table detects collisions. The author knew the cost was
real. It is still 44 ms on the cheapest command.

## Proposal

Generate the routing table **once**, into a single index file, at package
install or build time. The dispatcher reads one file instead of scanning 445.

The index is the natural shape for what is already there: a line per command,
`path<TAB>group<TAB>summary<TAB>args<TAB>flags`. It can be generated by a
static check, at package build, or lazily on first use with a mtime guard
against `/usr/bin/omarchy-*`.

**The fallback is not optional.** The dispatcher must fall back to the full
scan when the index is missing, stale, or fails to parse. Without that, the
fast path becomes a dependency, and a broken index breaks all 445 commands at
once instead of being slow. That is the difference between an optimization and
a single point of failure, and it is the whole reason to do this.

## Pros

- Every omarchy invocation gets faster, which includes everything in the
  keybindings file, everything the menu invokes, and every hook that shells
  out. It is the widest blast radius of benefit in this knowledge base and the
  narrowest blast radius of risk.
- ~45 ms → a few ms. For anything that invokes omarchy in a loop — a menu
  search, a panel refreshing device state — that is the difference between
  noticeable and not.
- The metadata becomes a **declared artifact** rather than something
  re-derived. It can be linted, diffed, and reviewed as data.
- Cost is near zero: no new process, no daemon, no cache invalidation problem
  beyond mtime.

## Cons

- **A generated file can drift from its source.** If a command is added and
  the index is not regenerated, the command silently becomes invisible to the
  dispatcher. That is the failure mode that actually matters.
- Install-time generation means an interrupted or partial install leaves a
  truncated index.
- A stale index is harder to diagnose than a slow one. "Why is this command
  not found" sends people down a path that does not exist.
- Bash still has to parse the index; the win is in file opens and `read`
  iterations, not in eliminating all of the work.

## Risk

**Low, and loud — provided the fallback exists.**

With a fallback and an mtime guard, every failure mode is "falls back to the
scan", which is the pre-change behaviour. It is slow, not wrong. That is the
property that makes this safe to do.

Without the fallback, the failure mode is silent: a stale index makes a
command unreachable, and `omarchy` exits non-zero with no obvious cause. This
is why the fallback is stated as a requirement rather than a nice-to-have.

## Evidence

```bash
# the cost, measured
for c in version "theme list" "plugin list"; do
  s=$(date +%s%N); omarchy $c >/dev/null 2>&1; e=$(date +%s%N)
  echo "$(( (e-s)/1000000 ))ms  omarchy $c"
done

# the scan, in the source
sed -n '1,20p'   /usr/bin/omarchy   # the metadata scan limit
sed -n '300,410p' /usr/bin/omarchy  # the glob and the route registration

# how much metadata there is to index
grep -c 'omarchy:summary' /usr/bin/omarchy* | wc -l   # 443
```
